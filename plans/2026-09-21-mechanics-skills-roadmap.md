## 0. 核心决策与边界

目标：把现有 v3.1.0 六技能套件收敛为能力声明可信、基础安装可用、证据来源准确、工作流可恢复、分发更新可追溯的研究辅助工具。

本轮建议维持“一个共享 Python 核心包 + 六个独立技能 + 轻量工作流”的架构，下一迭代优先修复交付与证据契约，不新增技能、不重写调度系统。核心包仍以标准库为基础，绘图、PDF 和数值检查保留为显式可选能力。文件组织与 CLI 兼容性优先于架构扩张。

适用范围是固体力学、断裂力学、弹性与应用数学的通用研究流程。个人项目的求解器、私有文献库与专属证据等级不进入通用核心；保留符号约定、证据定位和独立基准的共性规则。

权威顺序：本次用户要求与适用 AGENTS.md → HANDOFF.md 中仍有效的范围和纪律 → 可定位的当前代码与工件（判断实现事实）→ 已有 task_plan.md 的设计契约 → README 与 docs。文档相互冲突时记录差异；不能以旧计划的“完成”取代当前核实，也不能把源码现有缺陷当作应保留的规范。

本轮授权是检查与规划，新增本路线图。此文不自动授权实施、摄入全文、修改个人知识库、全局安装、推送或发布。实施范围仍须由用户后续指令确定；用户一旦授权具体范围，范围内常规编辑与针对性验证无需反复确认。

## 2. 推论与未知

### 推论

1. 项目已具备成套源码、CLI、技能与分发框架，下一轮应做可靠性收口。继续增加新技能会扩大现有契约漂移的范围。
2. 优先级最高的是基础依赖、更新保护、摘要来源与演示数据边界：它们直接影响“能否安装”“是否误覆盖”“研究者会否误认证据”，先于新数据库或复杂图算法。
3. 文档中的生产级、自动科学验证与完整端到端等表述，目前超出这次能确认的能力。适当收窄承诺是必要交付，不应靠增加测试数量维持原措辞。
4. 工作流有恢复机制的基本结构，无需新建调度服务。修正输入/输出指纹、工件命名、保存方式与状态传播，足以构成下一轮合理边界。
5. 数值矩阵检查、候选证据提取、文本规则审稿应保持可区分；明确“检查了什么、缺什么、由谁确认”比给统一 pass 更有研究价值。

### 未知

- 当前干净 Python 环境中的实际安装结果、全部历史测试是否仍通过；本轮没有运行。
- dist 的版本/hash 是否与当前源码相同、全局六技能是否同版本、远端 HEAD 是否与本地一致；本轮没有对账。
- Provider 当期认证、预算、重试规则与出口连通性；现有日期化文档并非本轮官方复核。
- 真实全文提取质量、复杂公式保真率、启发式误报漏报率、人工审稿收益；尚无本轮受控案例证据。
- PyMuPDF 等可选组件的实际分发方式及相关授权边界；不能从仓库 MIT 推导所有可选第三方组件均为 MIT。
- 下轮优先服务的真实研究案例与可用材料；先用公开或用户授权材料，缺材料则保留为待办，不用演示数据补齐研究结论。

## 4. 执行时的硬性纪律与闸门

1. 先落实 S1–S3 的 P0，再把新产物宣称为可正式使用的更新。不要为维持既有宣传而省略证据缺项。
2. 实施前确认当前工作区与并发修改；常规局部更新按授权范围执行。`git stash/reset/restore/clean`、强推、删除、未备份整文件覆盖等，必须按用户 AGENTS.md 先说明动作、原因、影响并取得明确回复；不能把运行脚本当作规避内部删除/覆盖的理由。
3. 构建使用新目录；同步先形成可审阅清单与备份。禁止直接执行当前尚无备份保护的全局 apply。源/目标路径需解析后验证属于本次约定范围，拒绝相互嵌套或越界目标。
4. 测试范围跟随实际改动。每阶段仅运行直接相关检查，绿色即止；失败先定位本次改动与外部状态，禁止清空共享工作区。相同方法连续失败三次应换方向，不增加无关验证。
5. 本轮未查官方政策、未读研究 PDF、未跑数值基准，后续报告仍需诚实标记。文本抽取、程序自洽、文献对源与外部独立证据不得互相冒充。
6. MIT 自有实现与第三方许可分开记录；不复制非商业许可上游的源码/提示文本。可选依赖不自动 vendor 二进制，不把仓库许可扩大为第三方许可结论。
7. 不读取或输出 `.env`、凭据、私钥、令牌等敏感文件；配置问题通过变量是否存在及脱敏诊断处理。
